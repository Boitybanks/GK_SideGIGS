# Assumptions & autonomous decisions

| # | Decision / assumption | Why |
|---|---|---|
| A1 | Marketplace model: **workers apply, customer selects** (not first-come auto-accept). | Customer trust requires reviewing the worker's portfolio before hiring; this also makes the portfolio load-bearing. |
| A2 | Pricing (changed again 26 Sep 2026 by the team; previously a 15% admin fee from the worker's pay, and originally 15% added to the customer): the client pays the job price with **nothing added**; SideGigs' **8% fee** is the only deduction from the provider's pay, so the provider receives 92% (R500 → fee R40 → R460). **No VAT is withheld from providers**: they are independent contractors, mostly below the VAT registration threshold, and VAT is not theirs to account for. If SideGigs registers for VAT, that concerns SideGigs' own fee, not the provider's earnings. Computed in the database (generated columns), rounded half-up to the cent. **Separation of concerns in the UI:** each side sees its own number — clients what they pay, providers what they receive; the other side's figure appears only as a preview while posting. | Team decision; fair to informal workers; clients cannot tamper with the fee. |
| A3 | Payments are a **clearly labelled simulation** ("held" → "released"/"refunded"). No real money moves. | Real payment/escrow is regulated and out of hackathon scope. |
| A4 | Location = curated list of South African areas with approximate centre coordinates; distance shown as "about N km". Exact addresses are **never public**. | No maps API key needed; protects residential privacy. |
| A5 | Accounts are created through a database function (`create_account`) that creates a confirmed Supabase Auth user, then the client signs in with the password. | New hosted Supabase projects require email confirmation and the default mailer only sends to team members; judges must be able to sign up instantly. The function validates input and hashes passwords with bcrypt (same as Supabase Auth). |
| A6 | Every account has a primary mode (worker or customer) and can switch mode in Profile. | Many real users are both; keeps the UI focused. |
| A7 | Seeded demo data is flagged `is_demo` and shown with a "Demo" badge; the Impact dashboard reports live (non-demo) figures separately. | "No fabricated user data presented as production data." |
| A8 | "Quantum encryption" is interpreted as **post-quantum cryptography** (NIST FIPS 203/204), not quantum key distribution (which needs quantum hardware). | Only PQC is implementable in a web app today. See architecture §7. |
| A9 | Supabase region eu-west-2 (London). | Closest available Supabase region to South Africa in the connector's list. |
| A10 | Real identity verification is **not** implemented; no "ID verified" claims or public identity badges. An optional `/identity-demo` checks ID format/checksum and permits a temporary local selfie; processing is explicitly simulated, nothing is persisted and completing it grants no privileges. "Verified record" means *created by SideGigs from a customer-confirmed gig*. | Honest trust labels; data minimisation; no mandatory demo gate. |
| A11 | Work-evidence photos: images only (JPEG/PNG/WebP), ≤ 5 MB, stored in a public bucket under the worker's own folder. | Safe file restrictions; portfolio evidence is meant to be public. |
| A12 | Shared demo logins are protected: credentials immutable, demo profiles read-only, no daily posting cap, local-scope sign-out. | Many judges use the same two accounts at once. |
| A13 | A verified record requires two-party confirmation: the worker marks the job done, then the customer confirms. | Stronger "verified" meaning; prevents a customer creating records alone. |
| A14 | Profile photos (workers and customers) are cropped to a 320 px JPEG in the browser, which strips EXIF/GPS, and stored in a public `avatars` bucket under the user's own folder. | Recognisable people at the door; no location leaks. |
| A15 | Users may upload up to 20 PDFs (≤ 5 MB, `%PDF-` signature checked) as qualification, ID document or other. SideGigs never checks them; ID documents are always private (DB constraint); others appear on the public profile only if the owner opts in. | Portable paperwork without any "verified" claim; POPIA data minimisation. |
| A16 | A Work ID (`SG-XXXX-XXXX`, 40 random bits) is issued by a trigger when a customer accepts a worker; only that pair can read it (RLS). They quote it when they call or message outside the app. | Lets each side prove they are the real match; anti-scam. |
| A17 | Forgot password uses Supabase's emailed recovery link → `/reset-password`, then signs out every session. Demo accounts are excluded. Delivery to real users needs custom SMTP and the reset URL in the Auth redirect allow-list. | Standard, secure self-service reset. |
| A18 | Jobs start and finish with an on-site QR handshake: when a worker is accepted the database issues one-time start and finish codes that only the customer can see. The worker scans the customer's QR code (or types its 6-character code) to start and to mark the job done. The customer still confirms completion. | Shows the worker was really there; confirmation stays two-party. |
| A19 | Sign-up requires an SA ID number, full name as on the ID, gender (male or female) and home address. The ID number is checked for format, a real birth date, the citizenship digit, the Luhn checksum and age 18+ in the browser and again in the database. It is **not** checked with Home Affairs. The ID number, legal name and address are encrypted in the browser; the database stores ciphertext plus a keyed hash (Vault secret) so one ID number opens one account. | Real-number checks without claiming identity verification; POPIA-minded storage. |
| A20 | If the chosen gender differs from the sex recorded in the ID number, or the profile name differs from the name on the ID, the person is told and asked to fix or confirm. Sign-up is never blocked for this, and no mismatch flag is stored. An ID number doesn't contain a name, so the name check compares the two names the person typed. | The team's choice: make people aware, don't exclude. |
| A21 | Providers can list priced **services**. They enter the amount they want to take home (R46–R46 000); the database derives the client price as the smallest price that pays exactly that after the 8% fee (R460 → R500). A client books a service with a date, area and encrypted address; there is no application step, so the gig is matched to the provider at once (Work ID, QR codes and held payment issued as usual). The provider can decline a booking before starting; the client can cancel before work starts; both refund the simulated payment. Providers stay independent contractors: they set their prices, choose and decline work, and SideGigs doesn't control their hours (LRA s200A). | "Vice versa" of client-posted gigs: whoever posts types their own number. |
